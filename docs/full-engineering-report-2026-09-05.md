## 1. Executive Summary

XAUDIT is a client-side, browser-only static pattern checker for JavaScript, TypeScript, React/JSX, a narrow subset of HTML, and pasted `package.json` manifests. Analysis runs in a Web Worker via a real AST parser (`@babel/parser` + `@babel/traverse`) for code, and a JSON-shape checker for `package.json` — never a regex-only engine, never a model call. Eight rule modules are active (`xss`, `dynamic-exec`, `sqli`, `secrets`, `node-command`, `auth`, `dependency-hygiene`, `html`), each documented with its own scope and disclosed false-positive/false-negative classes, both in-code and in `docs/rules/*.md`. **VERIFIED**: `npm test -- --run` passes 213/213 across 22 files; `npm run build` succeeds; `npm audit --omit=dev` (the exact command CI runs) currently **fails** with one moderate-severity transitive vulnerability (§9); no `fetch`/`XMLHttpRequest`/`WebSocket` call site exists anywhere in `src/` (grep-verified, matching a CI guard).

What it is **not**: not an AI product, not a vulnerability scanner with CVE/advisory data, not a data-flow/taint-analysis engine (tracing is exactly one variable hop, same-scope, never cross-function), not a general linter, not cross-file or whole-repository analysis (it analyzes one pasted block of text per run), and not proof that a "clean" result means secure code. Every rule module states this in its own limitations field on every finding it produces.

**Maturity label: Early usable developer tool with limited verified coverage.** This label is the project's own (`docs/self-audit-2026-09-03.md`), and this audit's independent re-verification of tests, build, and dependency posture does not contradict it — if anything, it surfaces a few things that self-audit had not yet caught (the CI-audit-gate failure in §9, several pieces of dead/orphaned frontend code in §4, and a git-history discontinuity in §7).

Strongest evidence of engineering quality: every one of the 8 rule modules documents its own detection method, its sanitizer/allowlist logic (or explicit absence of one), and its known false-positive and false-negative classes as inline comments that this audit could and did verify against the test corpus — not aspirational comments. The project's own self-audit found and fixed a real, live secret-redaction bug in its own local-history feature, and left a signed record of exactly what failed, how it was reproduced, and what test now guards it. That is unusually rigorous.

Most important unresolved risks: (1) the CI production-dependency audit gate is currently red (§9) — a merge to `main` today would fail that step; (2) two additional third-party libraries (DOMPurify, html2canvas, ~230KB combined) ship in the production bundle as an undisclosed transitive consequence of `jsPDF`, even though XAUDIT's own PDF code never invokes the feature that needs them; (3) `npm run lint` is not part of CI at all, so a growing amount of dead frontend code (§4) accumulates silently; (4) the zero-network-request claim, while true today by direct code inspection, is enforced by CI only via a source-level grep and a mocked-primitives unit test — the one test that would catch it in the *real* browser UI (Playwright e2e) could not be run in this environment and its current pass/fail state is unverified here.

Public copy (README, in-app disclaimers) matches the codebase closely and better than most projects at this stage — this audit's own line-by-line checks in §4B and §6D did not find an active overclaim. The one contradiction found (a landing-page rule-group count mismatch) had already been caught and fixed by the project's own prior self-audit before this review began.

## 3. Architecture

```
User pasted/typed text
  → byte-length validation             (analyze.ts:64-79 — 500KB hard cap; rejected outright, never truncated)
  → mode detection                     (analyze.ts:34-40 — "auto" | "html" | "script" | "package-json";
                                         a manually-forced mode can select the WRONG path — see §5B)
  → dispatch to Web Worker             (client.ts spawns worker.ts; postMessage with an incrementing requestId;
                                         stale responses from a superseded request are discarded client-side)
  → parser selected by mode            (html: no parser, regex/text scan only — rules/html.ts
                                         script: @babel/parser, unified JS/TS/JSX/TSX grammar — parse.ts
                                         package-json: JSON.parse + shape check — rules/dependency-hygiene.ts)
  → AST traversal / narrow rules       (6 script rules for "script" mode: xss, dynamic-exec, sqli, secrets,
                                         node-command, auth — analyze.ts's SCRIPT_RULES array;
                                         1 rule for "package-json"; text checks + per-block re-entry into the
                                         6 script rules for "html" mode's inline <script> content)
  → normalized Finding objects         (types.ts — every Finding required to carry whyItMatters/
                                         saferExample/limitations by the TypeScript interface)
  → deduplication                      (dedupe.ts — by ruleId + exact source line/column)
  → result returned to main thread     (client.ts resolves a Promise<AnalysisResult>)
  → React UI renders findings          (FindingsResults.jsx — plain JSX text interpolation, no
                                         dangerouslySetInnerHTML anywhere in this path)
  → optional, opt-in local persistence (storage.ts / storage/history.ts — localStorage, plaintext,
                                         gated behind an explicit user toggle, off by default)
  → optional client-side export        (pdf-generator.ts / sarif-generator.ts / json-generator.ts —
                                         Blob + URL.createObjectURL + programmatic <a download>, no network)
```

### Data Flow and Trust Boundaries

- **What enters**: a string of code or `package.json` text, typed or pasted into one `<textarea>`. There is no file-upload input element found anywhere in `CodeInput.jsx` — only `navigator.clipboard.readText()` (a paste-from-clipboard convenience button) and manual typing.
- **Where it is processed**: entirely inside the browser tab, off the main thread, in a Web Worker. Confirmed no network primitive is reachable from that code path (§6D).
- **What remains in memory**: the raw code, the AST, and all findings live only in the React component tree's state (`CheckerPage.jsx`'s `useState`) and the Worker's local variables — never assigned to any persistent store unless the user explicitly opts in.
- **What may be stored locally**: only if "Save report summaries locally" is checked — a timestamp, detected language, severity counts, finding **titles** (not full messages), and a masked ~120-character excerpt of the original input, run through three independent redaction passes first. Raw code is never written.
- **What exports may contain**: PDF — findings' title/message/saferExample/limitations, **not** `snippet` (verified: `pdf-generator.ts` never reads `finding.snippet`). SARIF/JSON — the full `Finding` object including the already-masked `snippet` field. Neither format can contain an unmasked secret through this path, since masking happens at rule-construction time inside `secrets.ts`, before a `Finding` object ever exists.
- **What does and does not leave the browser**: nothing does, on any of the three code paths checked (analysis, export, opt-in storage) — confirmed by direct code reading of every file in that path, not by trusting a comment.
- **External resources**: `index.html` loads zero third-party origins (own comment confirms this, verified against the file's actual content: no external `<link>`, no external `<script src>`). One documented exception: the production build bundles third-party JS *transitively* (DOMPurify + html2canvas via jsPDF, §9) — this is shipped code, not a runtime network call, but it is undisclosed anywhere in current docs.
- **Deployment-provider assumptions**: the entire security-header story (CSP/HSTS/clickjacking protection) depends on being hosted on Vercel specifically, via `vercel.json`. This is disclosed in `DEPLOY.md` but is a real, load-bearing assumption for anyone forking/self-hosting elsewhere.

## 4. Frontend Implementation Report

### A. User flows

1. **Landing page** (`src/pages/LandingPage.jsx`, route `/`) — marketing/explainer content plus CTAs into `/check`, `/rules`, `/privacy`, `/engine`, `/export`, `/tests`, `/docs`. No form state, no validation, no network calls of its own. Contains an interactive card-expand accordion (client-only React state) with no data-fetch behind it.
2. **Audit input/paste flow** (`src/components/checker/CodeInput.jsx`) — a single `<textarea>` bound to `CheckerPage`'s `code` state. "Paste Clipboard" reads via `navigator.clipboard.readText()`; "Insert Sample" fills the textarea from a hardcoded string constant (`SAMPLES`), never a network fetch. Size validation: live byte count via `TextEncoder`, compared against `MAX_SOURCE_BYTES`; the "Run Analysis" button is `disabled` when over limit or empty. No server-side validation exists or is needed (nothing leaves the browser).
3. **Mode selection / auto-detection** — four buttons (`HTML` / `JS / TS / React` / `package.json` / `Auto-detect`), plain state toggle, no debouncing or async behavior. See §5B for a real behavioral risk when a user manually selects the wrong mode.
4. **Analysis progress/status** — `CheckerPage.jsx`'s `handleRun()` calls `runAnalysis()` with an `onStage` callback; the Worker posts `"stage"` messages (`parsing`/`analyzing`/`rendering`) that update a `stageLine` string shown on the Run button itself. This is a real, driven-by-the-actual-engine progress indicator, not a fake `setTimeout` sequence (contrast with the old engine's fake 5-step progress bar, `docs/baseline-audit.md` #14 — this is a confirmed, verified fix).
5. **Findings report** (`FindingsResults.jsx` + `ReportOverview.jsx`) — severity/category bar charts (`ReportOverview.jsx`), then a list of finding cards sorted by severity. Error handling: a caught exception in `handleRun()` renders a generic `parse-error` result rather than crashing the page (`CheckerPage.jsx:44-46`).
6. **Finding detail / safer example** — each finding card has an inline, animated expand/collapse (`.analysis-expand-wrapper`/`.analysis-expand-inner`, a CSS grid-rows 0fr→1fr transition) revealing `whyItMatters`, `saferExample` (in a `<pre>` block, plain text), the masked `snippet`, and `limitations`. All rendered via JSX text interpolation (`{f.whyItMatters}` etc.), confirmed **not** `dangerouslySetInnerHTML` — no XSS surface in this path (verified by direct source read).
7. **Local history opt-in/out and clear-data flow** (`PrivacyControls.jsx`, `HistoryDrawer.jsx`) — a checkbox toggles `setSaveLocallyEnabled()`; unchecking it also calls `clearLocalData()` immediately (`storage.ts:56`). A separate "Clear local storage" button calls both `clearLocalData()` and `clearAuditHistory()`. `HistoryDrawer.jsx` reads `getAuditHistory()` fresh every time it opens (`useEffect` on the `open` prop) — flagged by ESLint's `react-hooks/set-state-in-effect` rule (a real, minor code-quality finding, not a functional bug — see §9/lint output).
8. **Clipboard copy behavior** — two independent implementations exist in the current tree: `FindingsResults.jsx`'s inline `handleCopyPrompt()` (the one actually wired into the live UI) and the orphaned `FindingDetailModal.jsx`'s `handleCopy()` (dead code, never imported — see §4B). Both call `navigator.clipboard.writeText()` on a locally-assembled string; neither ever contacts a network endpoint or a real AI API.
9. **PDF export** — `generatePDF()` (`jsPDF`, vector drawing API only — `doc.text()`, `doc.rect()`, `doc.roundedRect()`, `doc.addImage()`). Confirmed: never calls jsPDF's `.html()` method, so DOMPurify/html2canvas (bundled transitively, §9) are dead weight for this specific feature, not an active code path.
10. **JSON export** — `generateJsonExport()` wraps the exact already-computed `AnalysisResult` with a tool name, version, disclaimer, and timestamp. No reshaping, so it inherits the analysis engine's own risk profile exactly, adding none of its own.
11. **SARIF export** — `generateSarif()`, SARIF 2.1.0 schema, real per-`ruleId` `helpUri` into `docs/rules/<category>.md#<ruleId>` (verified these anchors exist — `docs/rules/README.md` lists every one). GitHub's `security-severity` extension field is populated with the project's own severity→score approximation, explicitly labeled in the source comment as "not derived from any CVSS scoring."
12. **Offline/PWA behavior** — not independently verified by this audit or the project's own most recent self-audit (automated-browser sandboxing blocked the check both times, for different specific reasons — see §2A). Treated as UNVERIFIED throughout this report, matching README's own "NOT VERIFIED, best-effort" language.
13. **Unsupported syntax or mismatched mode** — auto-detect correctly rejects non-JS/TS/JSX/HTML/package.json input with a `parse-error` status and a message including the parser's own line/column. Manually forcing "HTML" mode on non-HTML input is the one documented path that can silently return a clean, near-zero-finding result for code that was never actually examined by the 6 real script rules — a real, disclosed UX risk (§5B), now partially mitigated by the `html-script-content-not-analyzed` disclosure finding.

### B. Parser and mode behavior

- **Parser package**: `@babel/parser@7.29.8` + `@babel/traverse@7.29.8` + `@babel/types@7.29.8` (all resolved, verified via `npm ls`).
- **Configuration**: `sourceType: "unambiguous"`, `errorRecovery: false`, plugins `["jsx","typescript","classProperties","objectRestSpread","optionalChaining","nullishCoalescingOperator","topLevelAwait","decorators-legacy"]` (`parse.ts:57-72`).
- **TypeScript support**: syntax only, no type checker — confirmed, no `typescript` package invoked for type-checking anywhere in `src/lib/analysis/`.
- **JSX support**: on unconditionally (see below for the consequence).
- **Decorators**: `decorators-legacy` (not the newer TC39 `decorators` plugin) — a deliberate choice, documented in `parse.ts`'s own comment, because the legacy plugin supports parameter decorators (NestJS/Angular/TypeORM's real-world shape) and the newer plugin does not.
- **Parsing failure behavior**: returns `{status:"parse-error", error, ...}` with the parser's own line/column when available (`analyze.ts:176-190`) — no silent fallback, no partial analysis of an unparseable file.
- **Manual mode vs. auto-detect**: `detectMode()` only actually branches behavior for `"html"` and `"package-json"` (via `looksLikePackageJson()`, which requires a top-level object with `name` plus one of `dependencies`/`devDependencies`/`scripts` — not just any JSON object). Everything else always runs the identical 6-rule script pipeline regardless of what the user calls it — confirmed by reading `analyze.ts` end to end. This means the JS/TS/React "mode" buttons are cosmetic for script-shaped input (the parser accepts the syntactic union regardless), matching `docs/architecture.md`'s own stated rationale.
- **Can a scan show "0 findings" when no compatible analysis actually ran?** **Yes — Medium risk, confirmed by direct code reading and cross-referenced against the project's own self-audit (F-05).** If a user manually forces "HTML" mode on non-HTML script content (a Vue/Svelte single-file component is the canonical example), `runHtmlChecks()` finds no `<html>` tag (so viewport/CSP checks don't fire), no `<img>` tags, and `extractInlineScripts()` finds no literal `<script>` tags to extract — the result is `status:"ok"` with zero or near-zero findings, having never run any of the 6 real detection rules. This is now **partially mitigated**: if the input *does* contain literal `<script>` blocks and at least one fails to parse standalone, `html-script-content-not-analyzed` (info severity) is emitted per unparseable block. It is **not** mitigated for input that has no `<script>` tags at all (a `.vue` SFC's script content sits inside `<script>` tags and generally *would* trigger the disclosure — but pure JSX/TSX mis-saved with an `.html` extension, or content the extraction regex doesn't recognize as a script block, would not). Auto-detect does not have this problem: its own heuristic (`/^<!doctype html/i` or `/<html[\s>]/i`) does not match non-HTML content, so it correctly falls through to the script parser and produces an honest `parse-error` instead.

### C. Dependency-hygiene analyzer

Documented fully in the rule-registry table above and in the module's own extensive header comment (`dependency-hygiene.ts:1-46`). Explicitly not a CVE scanner — no offline advisory database is integrated anywhere in this codebase (confirmed: no advisory-data file, no CVE-lookup function, no network call). Checks are: unpinned version ranges, non-registry sources, suspicious `scripts` content, lifecycle-script presence (informational), and dev-tool-in-`dependencies` naming. Deliberately **not** implemented: missing-lockfile detection (this tool only ever sees pasted text, so "no lockfile pasted" and "no lockfile exists" are indistinguishable), and any usage-across-a-repository check (single-file input only). Test evidence: `tests/rules/dependency-hygiene.test.ts` (10 tests, all passing).

### C. CI pipeline

`.github/workflows/ci.yml` — triggers on push to `main`/`rewrite/**` and on PRs into `main` (this session's own branch, `mobile-responsive-and-new-pages`, matches neither push pattern; only its PR into `main` triggers CI).

Steps, in order: checkout → Node 20 setup → `npm ci` → `npm test` (must pass, no `continue-on-error`) → `npm run bench` (regenerates the report; **not committed back**, so CI's own regeneration and the repo's committed copy can silently drift if a rule changes without a manual `npm run bench` + commit) → `npm run bench:independent` (same caveat) → `npm run build` → install Playwright's Chromium → `npm run test:e2e` (uploads an HTML report as an artifact on failure) → `npm audit --omit=dev` (must pass, no `continue-on-error`) → a `grep -rnE` guard across all of `src/` for `fetch(`/`new XMLHttpRequest(`/`new WebSocket(`.

**What a failing CI run prevents**: since `npm audit --omit=dev` currently fails locally (§9) and has no `continue-on-error`, a fresh CI run today would stop at that step — meaning the final network-API grep guard (the very last step) would **not execute** on a run that reaches this point, though the test/build/e2e steps before it would still have run and reported their own results.

**Gaps CI does not cover**: no `npm run lint` step at all (so the ~10 files' worth of real lint findings in `src/`, §4B/§9, accumulate with no gate); no `tsc`/type-check step (no `tsconfig.json` exists to run one against); no automated check that the regenerated benchmark reports match the committed ones (a rule change could silently make the committed `.md` files stale); no automated re-verification of the live-deployed Vercel headers (only a local `curl -I` against `npm run preview`, done manually per `DEPLOY.md`).

## 12. Final Public-Facing Summary

### A. One-sentence description (max 35 words)
XAUDIT is a client-side, browser-only static pattern checker for JavaScript, TypeScript, React/JSX, HTML, and package.json — real AST parsing, eight narrow rule modules, zero network calls, no security guarantee.

### B. Portfolio description (100–150 words)
XAUDIT is a static code checker that runs entirely in the browser. Pasted JavaScript, TypeScript, React/JSX, HTML, or `package.json` is parsed with a real AST parser (Babel) inside a Web Worker — never sent anywhere — and checked against eight narrow, hand-written rule modules: DOM XSS, dangerous dynamic execution, a scoped SQL-injection heuristic, hardcoded secrets, Node.js command patterns, two weak-authentication checks, package.json supply-chain hygiene, and basic HTML attribute hygiene. Every finding states what matched, why it matters, a safer alternative, and — deliberately — what the check does *not* prove. There is no AI model, no letter grade, and no claim that a clean result means secure code. Findings export to PDF, SARIF 2.1.0, or JSON, all generated client-side. The project includes 213 automated tests, two benchmark corpora, and a published, evidence-based self-audit that found and fixed a real privacy bug in its own local-history feature.

### C. README disclaimer
> XAUDIT analyzes a defined, narrow set of patterns in JavaScript, TypeScript, React/JSX, HTML, and `package.json` — it does not attempt general vulnerability scanning, CVE lookup, cross-file data-flow analysis, or coverage of any vulnerability class beyond the eight rule modules documented in this README. Analysis runs entirely in your browser; nothing you paste is sent anywhere. This tool provides **no security guarantee of any kind**: every finding is a pattern match that requires your own human judgment, and a clean result does not mean your code is secure. See "Known limitations" above for the full, specific list of what this tool does not check.

## 13. Final Auditor Verdict

**Maturity rating: Early usable developer tool with limited verified coverage.** (This is the project's own label, from `docs/self-audit-2026-09-03.md`; this audit's independent re-verification of the test suite, build, dependency posture, and every rule module's source does not contradict it, and surfaces enough new, concrete gaps — §9's CI-audit failure chief among them — that a higher label would not be honest today.)

**Strongest evidence of engineering quality**: the density and accuracy of self-disclosed limitations. Every one of the 8 rule modules states, in its own source comment and in every `Finding` it produces, exactly what pattern it matches and exactly what it cannot see — and this audit's own cross-checking against the fixture corpus and both benchmark reports did not find a single instance of a rule module's own documented limitation being contradicted by its actual behavior. The project's self-audit found and fixed a live privacy bug in its own code and left a complete, honest record of it rather than quietly patching it — that is a genuinely uncommon level of rigor for a project at this stage.

**Single biggest remaining credibility risk**: the CI dependency-audit gate is currently failing (`npm audit --omit=dev` exits 1, via a transitive `fflate` advisory through `jspdf`), and the production bundle ships ~230KB of undisclosed third-party code (DOMPurify, html2canvas) that the project's own feature set never uses. Neither is a currently-exploitable vulnerability in XAUDIT's own code paths, but both directly undercut a project whose entire premise is "we say exactly what's true about our own code" — a supply-chain gate that isn't actually green, and shipped code no current document mentions, are the two things a skeptical technical reviewer would find first and would reasonably weigh most heavily.

**Can this truthfully be described as:**
- **"security tool"** — No. Too broad; invites exactly the overclaim this project's own rewrite exists to avoid.
- **"security checker"** — No, for the same reason, and because it implies broader coverage than 8 narrow rule groups.
- **"static-analysis prototype"** — Understates it. 213 passing tests, two benchmark corpora, and a published self-audit are not prototype-level rigor, even though the rule *coverage* itself is intentionally narrow.
- **"privacy-preserving code-analysis tool"** — **Yes, this is the accurate and defensible framing**, provided the transitively-bundled third-party code (§9) is disclosed alongside it. "Privacy-preserving" refers correctly to the verified absence of network calls and the verified opt-in/redacted local storage — it does not, and should not be read to, claim anything about detection completeness.

**Exact approved language for the website and college portfolio**: use §12A/§12B verbatim. Do not append "security," "AI," "enterprise," "comprehensive," or any percentage/accuracy figure to either.

**Prohibited claims that must not appear anywhere**: "AI-powered," "WebAssembly-based," "zero false positives," "enterprise-grade," "understands intent"/"context-aware," "real-time" (as-you-type) analysis, any specific accuracy percentage sourced from either benchmark report without its full caveat attached, "encrypted" local storage, "independent" applied to `docs/independent-benchmark-report.md` without its own qualifying sentence attached, and any claim that this tool provides a security guarantee, a pass/fail verdict, or a substitute for professional review.
